# Code Wiki 交互设计建议

日期：2026-10-24。性质：基于当前源码与实施计划的设计评审；尚非已实施功能清单。

最终边界更新：Code Wiki 面向技术人员；业务知识库后续另建，融合飞书与选定的已发布 Code Wiki。文档目录以 [固定目录规范 v1](CODE_WIKI_DOCUMENT_STRUCTURE.md) 为准。页面沿用“源文件 / Wiki / 知识图谱”，配置与进度使用现有入口和侧边抽屉，替代早期独立设置/生成页面方案。

执行计划见 [后续实施计划](CODE_WIKI_EVOLUTION_PLAN.md)。已收敛分析边界为明确提供源码的仓库，依赖库按需接入，不默认前后端共享。多轮增量以工具校验影响白名单、未变页原文/目录/版本和发布写集；下文“回退全量”指扩大分析与核验，不授权无差别重写整库。

## 设计判断

Code Wiki 的主要对象应是“基于一组固定代码版本生成、可审阅和追溯的项目知识”，而不只是仓库配置表单。读者需要快速理解系统，维护者需要控制输入范围、观察任务、审阅更新。页面应同时容纳这两种目的。

当前最大的缺口是生成过程不可解释。用户需要知道：输入是什么、正在处理什么、刚产出了什么、为何等待、下一步是否需要介入。单一阶段文字和累计完成数不足以回答这些问题。

## 现状证据与限制

- `frontend/src/views/knowledge/code-wiki/CodeWikiPanel.vue` 把分析服务、仓库绑定、活动任务和历史记录依次堆叠；任务区排在配置内容之后。活动任务每 5 秒刷新，展示 phase、完成页数与逐页结果。页面列表未区分正在检索、写作、校验。
- `frontend/src/views/knowledge/KnowledgeBase.vue` 默认进入 Wiki；“代码仓库”标签下挂载管理面板。离开该标签会卸载面板，其自身的任务轮询也随之停止。后台任务可继续运行，但观察任务需要返回管理页。
- `internal/application/service/code_wiki_generate.go` 的 `generateOnePage` 依次检索证据、调用模型、校验引用、暂存；本次核验的路径没有逐子阶段的持久进度。只改前端、提高刷新频率，无法获得这些事实。
- 暂停请求在阶段/页面边界检查；不能承诺点击后立即停下。暂停保留已完成页面；失败重试创建新批次并复用准备数据，不能把这两种操作都描述成“从断点继续”。
- 已有候选正文与证据详情接口，但当前管理页主要列状态；可以补充只读预览，必须标明未发布。暂存页状态不代表所有语义结论正确。
- `internal/application/service/code_wiki_publish.go` 已实现显式发布、事务调用及保留人工编辑策略；计划所称部署/可靠性验收待完成，不等同于这些代码尚不存在。
- 原索引早于新增 Code Wiki 文件，覆盖检查对这些路径报告未跟踪；本次判断以当前源码为准。未连接实际运行页面和任务，不据此判断已部署版本的具体故障。

## 信息架构

| 入口 | 用户目标 | 主要内容 |
| --- | --- | --- |
| 源文件 | 确定分析输入 | 复用 GitLab 同步源抽屉，配置仓库、分支、角色、过滤规则，查看快照与同步状态 |
| Wiki | 阅读技术文档 | 固定目录、阅读/编辑、版本、代码证据；轻量任务状态打开进度抽屉 |
| 知识图谱 | 查看文档关联 | 沿用文档关系图，后续独立代码图明确区分 |

任务卡片/状态入口打开右侧抽屉，展示阶段、逐页状态、活动、暂停/取消和审阅入口；切换三个标签仍可找到同一任务。模型、指令、预算及分析服务复用已有知识库 Wiki 设置入口，不新增独立设置页。

已有文档时默认阅读；首次为空时提供“连接代码 → 准备分析 → 生成文档”的引导和唯一下一步。已就绪的内置分析服务折叠为摘要，自定义服务映射放高级配置。

知识库公共区域保留任务摘要，显示“正在生成 / 等待 / 需处理 / 可审阅”。阅读页仍显示已发布版本；点击摘要进入同一任务，支持刷新、离开页面后重新找到任务。不要把普通 Wiki 的索引任务统计直接视为 Code Wiki 批次进度。

## 开始生成前

展示本轮仓库、固定 commit、排除项、输出语言、生成重点和预算。存在未就绪仓库时，明确阻断或要求用户确认排除，不能只因一个仓库就绪就让用户误以为全项目已参与。

“同步”表示准备某个代码版本，“生成”表示基于已准备输入产出文档。可提供“同步并生成”一站式入口，但应展示两个独立步骤及各自失败恢复方式。使用已有快照时明确提示，不暗示每次生成都会自动读取分支最新代码。

目录规划后默认继续执行，允许查看大纲；只有当用户需要强控制时再增加“确认大纲后继续”的可选关口。避免每页询问一次，打断后台任务。

## 执行中的反馈

建议层次：任务摘要 → 阶段导航 → 页面计划 → 当前动作 → 最近活动 → 诊断详情。

示例：

> 正在撰写《下单业务流程》；已通过校验 3 / 8 页。
> 本页已找到 12 条代码证据，正文生成中，接下来校验引用。
> 已用时 6 分 18 秒；最近活动 8 秒前。

- 主进度显示可验证计数，例如通过校验页数；3/8 不代表总时间完成 37.5%。目录尚未确定时不显示总页数；下载量、文件数与页面数不混成统一百分比。
- 页级状态：待开始、检索证据、生成正文、校验引用、候选就绪、失败、跳过。进度统计明确失败与跳过，不假装全部完成。
- 活动记录写已观察事实，如开始检索某仓库、读取指定代码、校验完成；不编造 Agent 的思考过程，不展示私有推理。原始工具参数、诊断和请求编号按需展开。
- 等待额度：展示原因、重试次数、下次计划重试时间；只有真实可知才显示倒计时。无充分历史数据时不给预计完成时间。
- 连接中断：显示最后确认状态和时间，明确后台可能继续；提供重新连接，避免用户重复创建任务。心跳正常与业务有进展分开表示。
- 长时间无新活动：提示当前步骤耗时及最后活动时间，依据服务心跳/超时判断，不能仅凭无新日志就宣布卡死。
- 暂停后先显示“暂停请求已提交，当前页完成后暂停”，服务确认后才变为已暂停。取消、放弃候选与暂停的影响分别说明。

## 生成后与发布

“生成完成”与“发布成功”分开。生成后进入候选审阅，展示新增/更新/失败/跳过页数、文档差异、引用校验、覆盖未知与未确认关联。

人工编辑冲突应定位到具体页面，提供当前版本与候选的对照；默认保留人工内容。现有 `keep` 策略会跳过冲突候选页，并不为同一页同时创建两个版本，文案应叫“保留人工修改”，避免“保留两者”的歧义。逐页合并属于新增能力。

部分失败单独命名，显示可用与不可用页；在明确确认前不将其视为完整新版本。若允许发布可用页，需要明确未更新页仍来自上一版。整批事务保证一次写入一致性，不保证失败页也已经更新。

阅读中的证据侧栏应显示仓库、固定 commit、文件行号与源码；区分“引用定位通过”“关系有双端证据”“尚未确认”，不生成没有依据的统一可信分数。文档关系图和代码调用图必须明确区分。

## 与尚未实现计划的衔接

### 已确认要求：前后端联合增量更新

用户已明确：前端和后端的跟踪分支都可能更新或切换。增量生成必须联合分析各仓库的变化及影响范围，更新受影响文档，不能只重生成发生变化仓库的说明页。此为目标要求，当前仍需实现。

- 比较基线是最近一次成功发布所绑定的完整仓库版本清单，而非最近一次同步或尚未发布的生成批次。例如上版 `frontend@F0 + backend@B0` 对比本轮冻结的 `frontend@F1 + backend@B1`；分别计算 F0→F1、B0→B1 的净变化。分支名是跟踪配置，commit 是实际比较对象。
- 更新开始时解析并冻结所有参与仓库的目标 commit，执行中分支再推进不改变本轮范围。公共库等关联仓库同样纳入清单与分析，未变化仓库仍作为调用另一端的验证上下文。
- 前后端差异共同作为影响分析输入：先定位变化符号、路由、接口、类型、配置及文件，再沿直接引用、调用/依赖与跨仓库关联扩展，合并并去重受影响页面。页面影响既可来自已存代码证据，也可来自目录规划与新增功能；不能只查旧引用，否则会漏掉新模块、新接口及需要新增的文档。
- 一侧接口或调用变化时，复核另一侧的对应端点与兼容性；更新接口说明、前后端交互、业务流程、架构等受影响页面。代码不兼容时如实标记，不替用户假定前后端已经适配。
- 处理删除、重命名与失效引用，明确哪些页面更新、新增、废弃或保留；人工编辑保护与发布冲突规则继续有效。
- 同时区分代码变化与生成规则变化。Provider、过滤范围、生成指令等改变也可能使既有结果失效，需要扩大重生成范围。
- 旧 commit 或证据无法读取、历史不可比、关系覆盖不足等情况下，不承诺可靠增量；扩大受影响范围，必要时回退全量并说明原因。大跨度分支切换不应仅因分支名变化一律全量，而应依据可比较性和影响分析可靠性决定。
- 联合清单表示本轮选定的前后端版本组合，不等同于已部署且兼容的组合；在任务中明确展示。

交互上，“更新 Wiki”先展示旧版与目标的仓库/分支/commit 对照，再显示影响分析结果：变化摘要、受影响文档、影响原因、计划新增/废弃页和分析限制；随后仅生成受影响文档，最后统一审阅发布。未变化页面可以沿用，但必须区分“内容未变、已针对新清单复核”和“仍基于旧快照”；不能把旧引用批量改成新 commit 或暗示其已验证。

增量任务抽屉增加“比较代码版本 → 联合影响分析 → 更新文档与引用 → 审阅发布”。页面列表可解释影响原因，例如“前端调用参数变化 + 后端路由参数变化，影响《下单业务流程》”。进度计数仅针对本次实际生成范围。

验收至少覆盖：仅前端变化、仅后端变化、前后端同时变化、两侧分别切换分支、接口变更传播、公共类型变化、新增功能无旧引用、文件删除/重命名、无变化跳过、失败不推进发布基线，以及后续再次更新时跨过未发布批次比较净变化。存在人工保留或失败页时，需保存页面实际证据版本及复核状态，不能将整份 Wiki 伪装成全部更新成功。

| 计划项 | 预留交互 | 上线前要求 |
| --- | --- | --- |
| 增量生成 | 任务范围“全量 / 更新受影响页面”、变更与受影响页预览 | 真实差异分析、影响范围与回退全量 |
| Webhook / 定时更新 | 设置中的更新策略；任务标记触发来源、排队与去重 | 触发调度和去重，生成与发布策略分离 |
| 代码问答 | 阅读页上下文提问，区分基于 Wiki 回答和查询源码 | 授权的源码工具、明确检索范围及证据 |
| 模板编辑器 | 设置中的文档结构；先提供现有指令配置 | 大纲持久化编辑、模板规则与校验 |
| 代码语义检索 / 独立代码图 | 文档搜索与代码搜索、文档图与代码图分开 | 对应索引和真实关系数据，不借用现有页面链接冒充 |

这些规划能力不应成为首版必须经过的步骤，也不应以可点击的已可用功能误导用户。阶段 0 的引擎/隔离实测、阶段 4 的部署验收仍须按实施计划核验。

## 实施顺序

1. 先解决可观察性：公共任务摘要、当前页面与子步骤、最后活动、限流/断连/暂停请求状态、完成/失败/跳过计数。
2. 在原有三个标签与同步源/Wiki 设置入口内重组仓库配置和任务抽屉；补候选预览、输入快照清单、失败诊断和发布前审阅。
3. 补持久任务事件、单页恢复与冲突对照能力，再接增量自动化、问答及代码图。

服务端新增结构化字段可包括 `current_page_key`、`step`、`step_started_at`、`last_activity_at`、`heartbeat_at`、`wait_reason`、`next_retry_at`、`attempt` 和 `pause_requested`。事件带单调序号、时间、仓库/页面、操作状态与简短摘要，支持有界分页、刷新恢复和去重。是否用轮询或事件流不应改变用户看到的状态语义；先补事实再改善传输方式。

验收重点：切换阅读仍能知道任务状态；刷新能恢复当前任务；限流与断连可区分；暂停未生效前不显示已停；失败不损坏已发布文档；候选未发布不会误当正式文档；手动编辑不被静默覆盖。

## 需要用户确认的产品取向

默认假设：维护者配置并审阅，读者主要阅读；生成默认自动执行，发布默认人工确认。优先确认主要使用场景是首次理解项目，还是持续追踪代码变更；这会影响首页和更新审阅的权重。后续再确认是否需要大纲审批及多角色发布权限。
