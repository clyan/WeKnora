# Code Wiki 固定目录规范 v1

确认日期：2026-10-24。状态：产品设计已固化，生成器与页面尚待按此实现。本文是后续目录生成、展示和增量更新的统一依据，替代此前的“业务流程 / 模块说明 / 仓库索引”方案。

## 1. 定位与适用边界

Code Wiki 面向技术人员，说明现有代码中的架构、实现、接口和功能链路。前端、后端及按需接入的其他仓库在同一知识库内联合分析，不拆成互相孤立的前后端知识库。

只分析明确提供源码并授权接入的仓库。未提供源码的第三方依赖仅记录已接入代码中的声明、版本、调用与返回/异常处理，不检索其内部源码、不推断内部实现；功能链路追踪到该边界即停止。完整稳定增量及工具校验执行规则见 [后续实施计划](CODE_WIKI_EVOLUTION_PLAN.md)。

后续另建业务知识库，以飞书文档与选定的已发布 Code Wiki 为输入，整理业务说明。业务术语手册、操作手册和业务 FAQ 不作为 Code Wiki 的强制目录。Code Wiki 的技术差异、未知与不兼容项如实保留，供技术人员核验。

本规范是 Wiki 的文档目录，不是“源文件”的源码文件树，也不是知识库页面标签。产品仍沿用“源文件 / Wiki / 知识图谱”，任务详情使用右侧抽屉，GitLab 配置复用同步源。

## 2. 固定目录

顶层分类、顺序与含义固定。`<仓库名>`、`<领域>`、`<模块>`、`<功能>`是根据实际代码生成的实例，不是文章标题。方括号说明是模板规则，不出现在正式标题中。

```text
项目概览/
  项目介绍与能力地图
  仓库清单与阅读导航

系统架构/
  系统组成与仓库职责
  请求链路与服务边界
  数据存储与外部依赖
  认证与权限架构

仓库文档/
  前端 · <仓库名>/                    [每个前端仓库各一份]
    项目结构与启动
    路由与页面
    业务模块/
      <模块>
    组件与状态管理
    请求封装与错误处理
    配置与构建
  后端 · <仓库名>/                    [每个后端仓库各一份]
    项目结构与启动
    路由组织与处理入口
    业务服务/
      <服务或模块>
    数据模型与持久化
    中间件与权限
    配置与外部依赖
    测试与部署
  依赖库 · <仓库名>/                  [仅明确提供源码并接入时]
    项目结构与使用方式
    类型与对外协议

  服务 · <仓库名>/                    [独立服务有对应仓库时]

  其他 · <仓库名>/                    [角色无法归入以上类型时]

    主要能力与依赖
    配置与运行说明

接口与跨端契约/
  前后端接口对照
```

例如订单领域可生成“创建订单 / 查询订单 / 取消订单”；模块与服务名称来自真实代码和已核验职责，不预设所有项目都有订单或用户管理。

### 固定与可变规则

- 顶层分类固定为以上七项，不由模型自由增加、改名、合并或重新排序。分类定义始终存在；没有实际内容的目录可在阅读时折叠或隐藏，不能为填满模板编造文章。
- 每类仓库的二级主题名称和职责按模板固定；是否生成该主题由代码与证据决定，不适用或证据不足的主题记录在生成计划与分析说明中，不生成空泛正文。
- 仓库、领域、模块和功能实例按实际项目扩展；首轮规划时小模块可合并相邻主题正文，但需记录归属，不创建重复页面。后续普通增量不得重新合并/拆分既有页面；确需调整时须有明确结构变化计划及审阅。深度拆页需有明确主题与足够证据。
- 依赖库不是前后端必然共用的仓库，需注明服务于前端、后端或具体仓库。只有前后端两个源码仓库时就只生成两份仓库目录；普通工具子目录归属其所在仓库。
- 一个仓库一个稳定目录，分支不是目录身份；切换分支不另建一套同名仓库目录。多个后端仓库分别展示，不能压成一篇“后端说明”。
- “仓库文档”统一承载局部实现，不再并设“模块说明”“仓库索引”；“功能链路”替代此前“业务流程”。
- “文档更新记录”关联持久生成/发布记录，展示页面变化，不要求模型每轮再写一份不可核对的总结。
- 目录规范版本为 v1。管理员后续升级规范需显式迁移；模型不得在普通增量更新中自行改变目录规范。

## 3. 内容唯一归属

| 内容 | 主要维护位置 | 其他页面如何引用 |
| --- | --- | --- |
| 系统组件、服务边界、全局依赖 | 系统架构 | 仓库和功能链路链接对应架构页 |
| 前端路由、组件、状态、请求组织 | 对应前端仓库 | 功能链路引用入口，不复制整份前端说明 |
| 后端处理入口、服务实现、模型、中间件 | 对应后端仓库 | 接口和功能链路链接具体实现 |
| 请求/响应、认证、错误约定、两侧兼容性 | 接口与跨端契约 | 仓库的路由页只维护组织与处理入口，不再维护第二份完整契约 |
| 一次操作从触发到结果的完整执行路径 | 功能链路 | 页面/服务文档维护链路索引与相关链接 |
| 单仓库启动、构建、测试与部署细节 | 对应仓库 | 系统级联调和部署页引用，补充跨仓库编排 |
| 系统级开发、联调和部署 | 开发与联调 | 不重复逐仓库命令的完整解释 |
| 版本、范围、未知与变更记录 | 分析范围与版本 | 各页保留自身证据版本和必要的局部限制 |

## 4. 功能链路与入口绑定

功能链路关联代码中的实际触发入口。关系为多对多：一个页面可触发多个功能，同一功能可从多个页面或多个前端仓库进入。前端页面不是唯一入口；API、定时任务、消息消费、CLI 等均可作为入口，不为后台功能虚构前端页面。

### 入口关联信息

| 字段 | 内容 |
| --- | --- |
| 入口类型 | 前端页面、API、定时任务、消息、CLI 等 |
| 所属仓库 | 稳定仓库 ID 与角色 |
| 页面/入口名称 | 订单详情、订单取消 API、订单超时任务等 |
| 路由或触发标识 | 页面路由、HTTP 方法与路径、任务注册或消息主题；未知时明确记录 |
| 触发动作 | 点击取消、提交表单、到达任务触发时间、收到消息等 |
| 代码位置 | 固定快照中的路径、行号、符号 |
| 关联功能 | 功能链路稳定 ID，可关联多条 |
| 核验状态 | 已核验、候选、未知；分别保存依据与缺口 |

路由、函数名或页面标题本身不是充分证据；需要结合路由注册、事件处理、请求封装、baseURL、代理重写、服务身份和后端处理上下文核验。动态注册无法确认时保留未知。

### 双向导航

- “路由与页面”列出页面、路由、组件、触发动作及关联功能链路，点击进入链路详情。
- 功能链路页列出所有已确认入口，点击定位页面/组件/处理入口的固定版本源码。
- 链路中的接口和服务链接到契约与仓库文档；必要代码证据沿用同一快照，不跳到分支最新代码。
- “源文件”按仓库展示源码文件树；与 Wiki 目录相互定位，但不以源码树替代文档目录。

## 5. 功能链路页固定正文结构

1. **功能与范围**：该链路做什么，涉及哪些仓库和版本。
2. **触发入口**：页面、路由、动作、API、任务或消息；可有多个。
3. **主执行链路**：事件处理 → 请求 → 后端入口 → 业务服务 → 数据访问 → 响应/界面更新，或对应的非页面触发流程。未确认环节明确断开。
4. **关键规则与状态**：输入校验、权限、状态转换、事务、幂等与并发行为，均以代码依据为准。
5. **异常与分支**：错误返回、界面提示、重试、超时和补偿；未实现的行为不补写。
6. **关联实现与代码证据**：接口契约、组件、服务、模型与固定 commit 的代码定位。
7. **已知限制与待核验项**：不兼容、动态行为与覆盖缺口。

图在有助于理解且依据足够时生成，区分已确认与候选；文档引用图与真实代码关系图不能混用。

## 6. 生成与增量约束

- 生成器按固定目录分配主题，模型只规划项目实例与有依据的页面内容，不能每轮重建整套目录。
- 为目录、页面、功能链路和入口关联提供稳定标识，标题、路径、分支和行号不直接作为身份；改名/移动应保留历史与链接，确认语义改变时才新增身份。
- 旧证据关联与变化代码共同参与影响分析，还要发现没有旧引用的新模块、新入口与新功能。
- 以前次成功发布的联合仓库清单为基线，分别比较前后端和其他已接入源码仓库变化，联合分析影响；未变化的一侧仍参与对应关系核验。
- 未受影响页不进入模型重写流程，正文原始字节、目录、标题、顺序、锚点、页面版本与旧证据保持不变；以程序检查及实际发布写集校验阻止误改。受影响页优先按稳定章节提交最小补丁，不整页润色。
- 无变化时不生成新页面修订；扩大分析范围不意味着整库重写。模型/规范升级使用独立迁移与审阅，不混入普通增量。
- 页面路由/入口动作变化时，更新页面索引及对应功能链路；接口、服务或模型变化时，向相关链路和契约传播，必要时扩大范围。
- 删除、重命名和入口失效需清理当前链接或标记废弃，保留历史证据。无法可靠判断时扩大只读核验范围或暂停等待影响审阅，不自动回退整库改写；更新范围仍须经过白名单与差异校验。
- 人工编辑保护继续生效。失败不推进成功发布基线；保留人工页、部分更新页保留实际证据版本与复核状态，不宣称全部内容已切到新版本。

例：前端新增下单参数，后端改变校验和状态流转，应检查前端订单模块、后端订单服务、数据模型、订单契约和“创建订单”功能链路；系统架构仅在边界/依赖变化时更新，无关链路复核后沿用。

## 7. 实现与验收

这是待实施契约，不代表当前固定 category 映射已经支持所有目录。实现时同步更新合法分类、目录路径元数据、规划/兜底大纲、发布归档、前端目录和历史兼容；不能只改提示词。

验收至少覆盖：

- 初次生成与规划失败兜底均遵循七个顶层分类及内容归属。
- 无前端、无数据库或未接入依赖库源码的项目不生成虚构主题，也不抓取未提供源码的第三方依赖。
- 多个前端/后端仓库分别可定位；切换分支不复制仓库目录。
- 一页多功能、多页同功能、纯后台触发均可正确建模和双向定位。
- 路由改名、入口删除、前后端契约变化能够联动更新对应链路与引用。
- 增量不随意改变目录或丢失页面历史，未核验关联不伪装成确认关系。
- 旧文档分类与链接可迁移或保留兼容入口，人工内容不被静默移动覆盖。
- 业务知识库后续可按稳定页面/链路标识关联已发布内容，不以任意最新开发分支作为客户当前能力的证明。
