# Code Wiki 知识体系设计提案 v2

日期：2026-10-25。状态：长期设计参考；当前实施范围、已完成项与限制以 [实施计划](FRONTEND_OKF_IMPLEMENTATION.md) 为准，本文未完成部分不能视为已实现。

格式依据：[OKF 官方规范](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)。产品文案、提示词与配置使用中性命名。

## 1. 理念与产品目标

参考文章强调维护期的知识生产，以项目/领域知识为底层、角色视图为中层、Skill 为消费入口，并通过人工确认和持续维护形成闭环。本提案以下内容是针对 WeKnora 的产品与实现建议，不是对文章实施细节或 OKF 官方规范的复述。

Code Wiki 的定位调整为：持续把授权源码和经确认的工程知识整理为可定位、可关联、可演进、可供人和 AI 按需读取的项目知识。

用户应能回答：

- 这个页面、接口、任务或消息入口做什么，执行到哪里？
- 一个字段、接口、数据表、消息主题变化，会影响哪些已知入口与链路？
- 哪些说法来自源码，哪些来自人工确认，哪些仍待澄清？
- 当前结论对应哪个代码版本，哪些内容已经需要复核？
- AI 为完成当前任务应读取哪些知识，必要时去哪里核对源码？

生成文档是知识建设的一个产物。文章数量、固定章节是否填满不作为完成标准。

## 2. 产品边界

保留一个 Code Wiki 知识库接入多个授权仓库。每个仓库有独立项目知识，跨仓库知识通过明确关系连接；无需强制让用户建立多个相互隔离的知识库。

Code Wiki 首期仍以研发使用为主，但其知识模型允许后续派生测试、产品视图。外部业务资料通过显式来源关联接入，不能把源码中猜出的业务动机当作已确认规则。

项目知识只分析提供的源码。第三方内部实现、未接入服务和动态行为无法确定的部分保留边界与待澄清项。基础知识变更触发派生视图复核，不意味着派生内容可以不经检查自动覆盖。

## 3. 知识对象优先于展示目录

建议先建立以下对象，再按角色和阅读任务生成导航：

| 对象 | 最小粒度 | 关键内容 |
| --- | --- | --- |
| 前端页面 | 一个真实路由/页面 | 操作、可见条件、权限、状态、请求调用点 |
| 执行入口 | 一个 API、任务、消息消费或 CLI 入口 | 协议、参数、校验、调用步骤、异常、数据落点 |
| 契约 | 一个可识别的调用协议 | 调用方、处理方、请求/响应、版本与兼容问题 |
| 领域对象 | 一个有证据的业务实体或状态模型 | 字段、枚举、状态转换、规则来源 |
| 资源 | 一张表、一个缓存键模式、消息主题等 | 读写、生产消费及其入口引用 |
| 链路 | 一个有真实触发点的业务过程 | 项目内步骤、跨项目连接、断点和异常分支 |
| 决策与经验 | 一个可确认的决策或问题 | 背景、依据、适用边界、负责人、确认记录 |
| 待澄清项 | 一个具体证据缺口 | 问题、相关对象、候选依据、所需确认 |

知识条目拥有稳定 ID，标题、目录、行号和 commit 均不是身份。一个条目可出现在多个视图，正文及事实来源保持唯一维护位置。

Markdown 是可阅读、可导出的表达；结构化记录负责身份、类型、来源、关系和生命周期。第一期继续使用现有数据库和 Wiki 阅读器，不要求立即改为 Git 文件存储。

## 4. 导航与知识关系

建议阅读导航逐步调整为：

```text
总览与阅读导航
项目知识
  前端仓库 → 页面 / 操作 / 接口使用 / 组件与状态
  后端仓库 → API / 任务 / 消息入口 / 模型与资源
领域与链路
  领域 → 场景 → 项目内和跨项目链路
资源与影响
  表 / 缓存 / 消息 / 外部协议 → 读写及上下游
决策与经验
待澄清与待复核
```

现有七类固定目录可暂作兼容阅读视图，后续通过独立迁移转换。它们不再约束知识对象数量或要求模型预先决定全部主题。

反向索引来自明确关系记录：例如页面调用接口、接口写入表、任务发布消息、消费者订阅消息。文档超链接继续服务阅读，但不能单独证明代码调用或业务影响。

跨仓库匹配需要核验协议、服务身份、路径/主题、配置解析与版本。关系状态区分已核验、候选、未知；有界采样不能标记全仓覆盖。

## 5. 生产流程重设计

建议把当前“模型规划目录 → 检索 → 生成文章”调整为以下工作流：

1. 冻结输入：仓库、分支、commit、过滤、解析器及生成规则版本。
2. 发现并登记入口：读取路由注册、任务注册、消息订阅、页面路由和调用点；尽可能分页盘点，不以一次模型返回代替清单。
3. 形成可检查的工作清单：展示已发现对象、来源、未知范围、预计处理量；用户可选择分批建设。
4. 逐项整理知识：为一个入口/对象读取有界源码、解释实现、提取资源关系并校验证据。
5. 构建反向关系：资源到入口、契约到调用方、页面操作到处理端；保留每条关系依据与缺口。
6. 组合链路：以已整理对象及关系为输入，生成项目内和跨项目链路；按需核对源码，未知节点明确断开。
7. 生成导航和摘要：从已有知识对象派生总览、目录、索引和阅读路径。
8. 审阅与发布：显示对象/关系/文档变化、待澄清项和覆盖说明，确认后推进版本。

每一步有可持久化的工作项，支持检查点恢复、对象级失败与重试。现有发布完整性门禁保留；若新增分批发布，必须以显式选定且依赖完整的批次为单位，未处理内容保持原版本并展示待更新状态。

不为每个函数建立文档；对象粒度围绕可消费的入口、契约、模型与资源。页数预算改为每批预算，不能用总页数上限把未发现/未处理对象伪装成不存在。

## 6. 增量与生命周期

保留现有快照冻结、联合净变化、章节白名单、人工编辑保护和事务发布。

在此之上增加“变更源码 → 事实/关系 → 知识对象 → 派生视图”的依赖映射。新旧关系共同参与影响判断，避免删除边后丢失旧影响路径。未知覆盖进入待复核，不自动判无影响。

每个条目分别保存：来源版本、最近核验版本、负责人、人工确认来源、状态及关联关系。正文未变但完成复核时只记录核验结果，不制造正文修订。

建议状态包含候选、已核验、待澄清、待复核、已归档。源码证据支持的实现事实与人工确认的业务规则分开记录，源码不能证明的规则不得标为自动核验通过。

经确认的需求说明、设计决策、排障记录可作为补充来源进入候选，再由负责人审阅；不能覆盖代码现状或把未发布方案写成当前行为。

## 7. 面向 AI 的消费能力

在现有问答能力上增加按知识类型和稳定 ID 的读取接口：先获取项目/领域索引与摘要，再读取目标条目、关联对象和必要源码。响应携带来源版本、核验状态和已知缺口。

后续可封装为知识阅读、接口追踪、影响分析、回归建议等 Skill。Skill 使用同一知识来源与权限，不能另维护一套平行事实。

导出时可提供带元数据的 Markdown、导航索引、关系链接和变更记录。是否宣称兼容 OKF，需另行核对其官方规范和版本；本提案不把文章介绍视为格式标准。

## 8. 保留、替换与实施顺序

| 当前能力/规则 | 建议 |
| --- | --- |
| 多仓库授权、快照、分析器、代码证据 | 保留并作为知识生产基础 |
| 候选、人工审阅、增量白名单、版本保护 | 保留并扩展到对象/关系 |
| 先调用模型规划固定文章目录 | 替换为入口/对象发现与工作清单 |
| 七类目录作为知识模型的核心 | 降为兼容视图，提供显式迁移 |
| 文档引用图 | 保留，另外建设有类型和证据的关系 |
| 一轮长任务和全局页数上限 | 演进为分批、可恢复、可显示覆盖的工作项 |
| 业务知识必须另起一套事实 | 评估调整为同源派生视图，仍保留来源和权限边界 |

实施建议：

1. 优先实现项目知识底层：真实入口盘点、对象身份、逐对象文档、任务清单及覆盖状态。
2. 再建设资源反向索引、项目内链路与有证据的跨仓库契约连接。
3. 完成增量依赖传播、负责人确认、待澄清和过期复核。
4. 最后扩展角色视图、工程过程知识沉淀和 AI/Skill 消费接口。

第一期验收以“发现了多少入口、哪些已核验、哪些未覆盖；随机入口能否还原真实执行与资源落点；变更后能否定位需复核条目”为核心。精确率、覆盖率和影响召回分别记录，不以文档数量或通用提速比例代替实际验证。

## 9. 待讨论的产品决策

建议第一期聚焦项目知识与资源关系，业务/测试角色视图后续再做，但数据模型预留派生关系。需要确认是否接受这一分期，以及现有七类目录由强制知识结构降为兼容视图。

本提案不触发源码生成器改造、现有知识库迁移、重生成或删除。
