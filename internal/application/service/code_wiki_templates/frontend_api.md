按以下结构撰写 API 专题。可以包含一组有实现关联的接口，不能把整个仓库的请求堆成一篇。

## 用途与代码位置
说明前端用途、请求定义及封装位置、已确认调用页面/操作。未找到调用者时写明查找范围，不宣称全项目无人调用。
## 接口清单
表格：函数｜method + path｜用途（仅代码可查证）｜实际调用位置。
区分源码路径、封装追加前缀及尚未确认的环境地址；前端声明不等于后端已经实现。
## 真实入参（按调用点）
每个调用点分别列：字段路径｜实际传入表达式/来源｜类型依据｜默认值及转换｜传入条件｜覆盖/展开顺序。
追踪参数对象的构造函数、对象展开和请求封装追加字段。类型声明、实际传入和未知动态字段分开；不能将不同调用点字段并成全部必传的后端 schema。缺少构造逻辑则继续取证或明确未知。
## 响应使用与失败处理
列出调用方实际读取的字段、状态更新、错误提示/捕获、加载状态和可确认重试；类型中存在但未使用的字段不能写成实际使用。
## 关联专题
仅链接已经存在且有权访问的页面、组件和流程。
## 待确认
列出未知字段、缺少的调用端或后端边界及需要补查的代码，不猜业务解释。
