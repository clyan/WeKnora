按证据选择下列一个架构主题，一篇一个主题，不把全部模板合成一篇，也不为凑目录生成空主题。按所选主题的专用结构展开，最后保留关联专题和待确认。

### 主子应用关系（仅微前端适用）
- 应用清单：应用｜角色（主/子）｜技术栈｜代码位置｜配置入口及环境。部署配置不等于线上生效事实。
- 加载机制：微前端方案、注册位置、实际加载时机及失败处理；普通 npm 组件集成不等于微前端。
- 路由衔接：主应用路由前缀｜子应用｜内部路由｜衔接条件。
- 共享依赖：主应用实际提供的依赖、运行时与版本限制，区别于仅在 package.json 中声明。
- 生命周期：挂载、卸载、更新的动作与资源清理。

### 应用间通信
- 通信机制清单：机制｜事件/字段名｜发送方｜接收方｜数据结构｜用途。
- 共享状态：状态字段｜提供方｜使用方｜读/写/订阅关系。
- 使用约束与清理：订阅/取消、消息过滤、载荷校验、错误处理；只有一端源码时说明另一端未知，不按事件同名补边。

### 技术栈矩阵
- 矩阵：应用｜框架及版本｜构建工具｜UI库｜状态管理｜路由｜请求库｜测试工具。
- 分清 package.json 声明范围、锁文件解析版本和实际导入/执行；没有锁文件或执行证据时不称为实际安装/运行版本。
- 版本差异提示：各应用或包的依赖差异及可查证约束，不自动断言兼容或冲突。

### 基础设施（一个机制主题一篇）
- 职责与边界：请求层、登录与权限、全局状态/store、埋点、错误处理、国际化或构建等，仅选择有实现的主题。
- 关键机制表：机制｜实际入口/调用路径｜行为与条件。
- 对业务代码的约束：区分实际执行的约束、配置声明及观察到的用法。
- 被谁使用：已确认 API 模块、页面或组件；store 主题补字段、初始值、getter/action、读写方及清理。

### 跨仓库依赖
- 后端服务/网关：目标｜前端用途｜使用的 API 模块｜配置与映射依据；仅前缀相同不能确认服务归属。
- 内部包/私服组件：包名｜声明/解析版本｜用途｜实际引用位置｜源码可访问边界。
- 其他前端仓库：共享组件、子应用、公共配置的真实加载/引用关系，不把未授权仓库当作已经核验。

### 路由表（有独立主题需要时）
- 路径｜页面｜注册/挂载条件｜路由权限｜懒加载｜重定向/降级。
- 动态路由、菜单与实际可达性分别说明；前端路由权限不能证明服务端授权。
