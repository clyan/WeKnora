# Proposal

## Why

当前规划阶段可以多轮搜索和阅读，正文却依赖有限片段一次成文，前期分析成果未充分复用，复杂操作、权限和真实参数容易遗漏。改为按知识主题持续取证、保存轻量检查点并受控并发；只写当前源码可查证的事实，未知业务含义交由人工补全和抽样纠错。

## What Changes

- 知识库区分项目代码模式与领域模式：项目模式从源码提取事实，领域模式仅组合已发布项目事实及跨项目依赖，不重新提取或改写底层实现。前端/后端是项目模式的仓库角色，不是两种顶层模式。
- 建立不可被自定义提示词放宽的来源政策：业务事实只能来自冻结代码快照中的实现、真实使用关系与相关配置；文档、说明性注释、Mock、样例、测试断言不作为业务事实证据。
- 初步发现页面、接口及组件主题，再沿入口、操作、权限、调用点和参数来源持续补查；目录允许调整，规划读取成果复用于深入分析与正文，不要求全仓重复分析两遍。
- 目录规划升级为入口与依赖驱动的模块簇、按模型预算拆分的独立并发批次和有界统一核对。公共依赖独立引用，无入口或关系缺口保留待查；超限依次缩批、拆簇、分页结构导航，提供方仍拒绝时降低预算并有限重试，无法处理仅暂停受影响批次。批次检查点独立提交，统一核对主题身份、重复范围和跨批关系后确定初步目录；增量复用已有身份，不因分批重排重写未变目录。
- 以每个主题的版本化分析检查点保存已查明结论、证据清单、已发现项、待追踪问题和未知边界；复用现有任务存储及已建基础，不将独立事实数据库、完整语法树落库或业务本体建设作为前置条件。codebase-memory 保留为默认索引/关系定位工具，结论仍须回读源码。
- 按当前问题组装上下文，估算所选模型 token 容量并预留工具返回与输出；超限拆分、分页或保存检查点续查，禁止静默截断关键证据。模型会话历史和摘要不能替代证据。
- 主题就绪后按分析记录成文，证据不足返回同一分析循环；替换固定最多十二条片段一次成文路径。相关专题完成后再生成概览和导读，保留目录树、预览、审阅、发布和 OKF 导出。
- 复用普通 Wiki 的工作池，抽取认领后的租约生命周期、续租停止、并发占用和所有者锁释放机制；批次与主题保留各自的存储认领条件和配置。Code Wiki 默认单库三个主题并发，不同主题独立上下文，同一主题仅一个有效写入者。保留共享模型并发、任务调用预算和提供方限流退避；不建设全局每分钟请求数/token 限速。
- 后端仓库可用后独立抽取接口、调用链、数据读写落点与依赖；缺少后端源码时不从前端、Mock、文档或业务常识补造后端结论。
- 为未知业务含义建立待澄清问题、人工解释、源码复核与抽样纠错闭环；人工解释单独标注，不能未经源码核对便升级为代码事实。
- 按阶段交付：一是来源约束及页面/API 闭环和基础审阅，二是组件与架构/通信/流程及关系驱动增量，三是后端抽取、前后端关联与完整人工核对闭环；每阶段有独立验收门槛。
- 进度改为总体状态、并发主题列表和可展开详情；主题分别展示排队/执行/等待模型调用/暂停/失败等状态、动作及源码位置，事件可分页恢复且不泄露内部推理。动态发现主题不伪装成固定百分比，任务完成不代表全项目语义完整。所有 Code Wiki 页面文案以易懂为验收要求：说明当前情况、原因和下一步，明确是否自动恢复；技术详情按需展开，不直接展示内部状态码或原始报错。
- **BREAKING**：新任务采用新的事实模式及证据政策版本；旧任务可以查看，但旧证据、旧生成正文不能直接当作新流程的可信基线。不得静默沿用旧的片段成文后备路径。

## Capabilities

### New Capabilities

- `frontend-source-evidence`: 当前实现的来源资格、证据边界、强制政策及版本一致性。
- `frontend-fact-inventory`: 主题检查点中的结论、操作、接口参数、证据与范围；能力名保留，不要求独立事实数据库。
- `frontend-analysis-workflow`: 持续追踪、上下文预算、检查点、受控并发及前端多主题执行进度。
- `frontend-knowledge-authoring`: 按共享事实生成专题、概览、索引和覆盖报告，并联通预览与 OKF。
- 领域模式的行为契约一并纳入 `frontend-knowledge-authoring` 和增量规格：冻结来源库发布版本，一级域组织大链路、二级域组织细链路，按已确认 HTTP/RPC/JSF、MQ、调度及回调边拼接；未知连接保留断点，不凭名字或时序常识补齐。
- `frontend-knowledge-incremental`: 首次基线、增量影响分析、失效处理、版本升级及人工修改保护。
- `backend-code-facts`: 有后端源码时抽取接口、调用链、数据落点与依赖，区分实际实现与静态声明。
- `code-knowledge-review`: 待澄清问题、人工补充、抽样核对、纠错与复核记录。

### Modified Capabilities

无。当前 OpenSpec 主规格库为空，上述为首次建立的行为契约；不代表相关实现全部从零开始。

## Impact

- 平台服务端：`internal/application/service/code_wiki_frontend*.go`、`code_wiki_generate.go`、基线/影响分析/补丁/发布/OKF 服务，相关类型、仓储接口及实现、任务查询接口和 PostgreSQL/SQLite 迁移；后续增加后端代码事实分析适配及人工问题/复核记录。
- 前端：默认模板与生成设置、Code Wiki 任务进度、目录、预览和覆盖详情；沿用已有多语言机制。
- 分析：首批支持 JavaScript/TypeScript/JSX/TSX 的静态结构分析，复用受控文件读取及代码索引。后端阶段首批支持 Go 的 HTTP 注册、直接调用、可定位数据访问和依赖；其他语言、动态代码与不可访问依赖明确记为未支持或未确认，不声称已完整分析。
- 配置：用户仍可编辑内容偏好和提取重点，但不能授权以文档、注释或 Mock 证明业务事实；新执行冻结政策与分析器版本。
- 数据：优先扩展现有任务存储，按主题保存检查点、证据和依赖清单；允许必要的主题任务/事件记录及索引，不新建通用事实/关系账本。已建事实记录保持兼容读取，不自动删表、清理历史或作为已核验结论使用。本提案不自动触发生成、发布或外部模型调用。
- 后续阶段四交付领域模式；项目库以绑定发布版本的主题结论和结构化跨项目依赖清单提供来源，不要求通用事实数据库。领域生成不直接扫描源码或从 Markdown 反推事实，补证需求交回来源项目库，来源更新标记链路待复核，访问不得突破来源权限。
- 非目标：无源码的后端实现推断、从技术调用自动猜测业务含义、线上行为保证、全语言通用分析器、任意动态数据流的完整证明、完整 OKF 导入，以及固定篇数或强制微前端模板。
