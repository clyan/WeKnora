# Spec Delta

## Purpose

将代码无法证明的业务含义交由人工澄清，并通过可追溯的抽样核对与纠错提高知识质量。分别保存代码事实、人工解释和未解决问题，防止人工意见被误标为代码证明，也避免少量样本通过后宣称全库已验证。

## ADDED Requirements

### Requirement: 不确定业务含义进入问题清单

系统 SHALL 为代码不足以解释的业务含义记录具体问题、已确认实现、未知原因及关联专题，不得依据命名、注释或常识补全。问题 SHALL 支持待澄清、已补充和已复核状态及版本历史。

#### Scenario: 状态数值没有可证实的业务含义
- **WHEN** 实现只确认 status 等于某数值时禁用按钮，没有实现支撑业务解释
- **THEN** 文档描述实际判断条件，并询问该状态的业务含义，不自行解释为“审批通过”

### Requirement: 人工解释与代码事实分层

系统 SHALL 保存人工补充者、时间、解释内容及关联版本，并在阅读与导出中明确标注人工解释；只有获得当前实现证据并完成复核，相关可查证部分才能升级为代码事实。人工解释不得绕过来源校验覆盖矛盾实现。

#### Scenario: 人工补充业务术语
- **WHEN** 用户解释某状态的业务名称但未提供实现依据
- **THEN** 系统将其显示为人工业务解释，关联现有条件事实，不标为代码已证实

### Requirement: 抽样核对可记录可纠错

系统 SHALL 支持按页面、调用点、权限条件、数据落点或高风险未知边界选择样本，记录样本范围、主题分析修订、复核人和通过/纠错/未确认结果；发现错误后 SHALL 关联受影响的主题结论、证据、专题和索引，生成新分析修订及待审阅候选，不要求独立事实数据库，也不得直接覆盖已发布正文。

#### Scenario: 发现字段来源描述错误
- **WHEN** 复核者发现文档将固定值误写为表单值
- **THEN** 系统登记纠错、关联该调用点和页面/API 专题，修正候选经来源与发布检查后生效，保留原版本与复核记录

### Requirement: 抽样结论不扩大为全库保证

系统 SHALL 单独展示抽样数量、范围、未复核部分和对应代码版本；源码或关联事实变化后 SHALL 标记旧复核结果待复查，不能继续标为当前版本已验证。

#### Scenario: 样本通过后代码变化
- **WHEN** 十个样本通过后其中一个参数构造发生变化
- **THEN** 该样本标记待复查，其余结论仅对原有版本范围有效，不宣称整个知识库已经验证
